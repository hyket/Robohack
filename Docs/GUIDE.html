От первого Docker-образа до автономного прохода по трассе.

Начать с T1

Как проходит хакатон

Команда готовит один Docker-образ с программами для робота Unitree Go1. На каждое испытание организаторы запускают его с именем задания рядом с симулятором. Симулятор даёт показания датчиков и исполняет команды, а судья (Judge) задаёт сценарий и оценивает результат. Как устроен обмен

Сейчас в Robohack реализован T1. Это общий допуск. Дальше работу можно разделить: в MuJoCo команда учит робота безопасно шагать, в Gazebo — определять своё положение и находить путь.

Пять заданий

  1. T1. Подготовить контейнер

    Собрать образ для linux/amd64 и вызвать /entrypoint.sh ping без сети. За 10 секунд запускатель должен получить JSON со списком поддерживаемых заданий. Так команда получает допуск.

  2. T2. Защитить суставы

    В MuJoCo судья подаёт команды для 12 суставов. Фильтр команды пропускает безопасное движение и удерживает последнюю безопасную цель, если вход пропал. Проверяют углы, переходы между позами и частоту выхода.

  3. T3. Пройти три метра

    Теперь цели суставов задаёт обученная политика. Она получает желаемую скорость и передаёт команды через фильтр из T2. В каждом из десяти независимых запусков проверяют, прошёл ли робот 3 м вперёд без падения.

  4. T4. Оценить движение

    В Gazebo роботом управляет судья. Программа команды по датчикам восстанавливает фактическую траекторию. Её сверяют с движением робота и измеряют, насколько оценка смещается за 10 секунд после остановки.

  5. T5. Найти путь и распознать метки

    Nav2 использует одометрию из T4, чтобы вести робота к цели по неизвестной трассе. Камеры по пути считывают метки ArUco. Судья проверяет положение и ориентацию на финише, увиденные метки и контакты с препятствиями.

Проверка и сдача

Сначала проверьте каждое заявленное задание на локальном стенде. Затем соберите образ из опубликованного коммита и убедитесь, что он скачивается из Harbor по digest — идентификатору этой сборки. В личный кабинет передаются ссылка на коммит и команда загрузки образа. Порядок сдачи

Архитектура решения

На одно испытание запускается одна пара контейнеров. В Participant работает код команды для выбранного режима. В Simulator/Judge симулятор рассчитывает физику и показания датчиков, а судья задаёт испытание и оценивает результат. Между контейнерами идут публичные сообщения ROS 2 через Cyclone DDS. Отдельный вызов ping читает возможности образа через stdout. Сегодня в репозитории реализован этот вызов. Схемы T2–T5 описывают целевую архитектуру. T4 изолирует измерение движения. Одометрия связывает корпус trunk с локальной системой odom. Симулятор публикует положение датчиков относительно корпуса. Из этих преобразований можно, например, перевести точку из системы лидара в odom. За команду скорости в этом режиме отвечает Judge.

T5 добавляет движение к цели. Для показанного варианта с лидарной локализацией участник оценивает положение системы odom относительно map. Теперь Nav2 через цепочку map → odom → trunk может сопоставить текущую позу корпуса с заданной целью. Планировщик выбирает путь с учётом препятствий, контроллер выдаёт очередную /cmd_vel, CHAMP исполняет её. Новые измерения обновляют позу и препятствия перед следующей командой. Параллельно детектор отправляет Judge ID меток, видимых на текущих кадрах. Это отдельный выход для оценки, поэтому навигация может обрабатывать цель даже в кадрах без меток. Локальный стенд и порядок измерений

Как читать граф ROS 2

Узел (node) может подписываться сразу на несколько топиков и публиковать свой результат. Имя топика говорит, где искать данные, тип сообщения — как читать поля. DDS доставляет сообщения между участниками одного ROS-домена. QoS задаёт правила доставки и очередей. Если издатель предлагает best effort, подписка с требованием reliable с ним не соединится.

В оболочке Simulator с подключённым окружением пройдите от списка узлов до одного измерения:

ros2 node list
ros2 topic list -t
ros2 topic info -v /lowstate
ros2 interface show unitree_go/msg/LowState
ros2 topic echo /lowstate --once

Выполняйте пример в MuJoCo. В первой команде ищите работающие узлы, во второй — имя и тип канала, в третьей — число издателей и совместимость QoS. Последняя команда подтверждает, что сообщение действительно пришло. Поля LowState описывают измеренное состояние суставов. Аналогично в Gazebo проверьте /imu/data типа sensor_msgs/msg/Imu.

Participant содержит алгоритмы команды. Simulator публикует датчики и исполняет команды. Judge на официальном стенде задаёт испытания и измеряет результат. В публичной сборке роль источника тестовых команд берёт на себя команда. Истинную позу из публичной симуляции можно записывать отдельным локальным измерителем. Решение внутри сдаваемого образа должно работать только по публичным датчикам. Описание стенда

  1. Для стенда организаторы проверили Ubuntu 22.04 на amd64. Нужны Docker Engine, Compose с поддержкой !reset, Python 3.10+ и Git. Сначала из каталога Robohack собрать Participant по README.
  2. Следующие команды выполнять на хосте, в отдельном каталоге для стенда. Доступ к реестру нужен при подготовке образов. На текущем T1 уже можно проверить саму симуляцию.
git clone https://github.com/Urika000/go1-simulator-public.git
cd go1-simulator-public
git checkout 3473f086fd8a111592b4b9d822500c79f20c811a
export SIM_IMAGE=registry.cookcloud.ru/go1-hackathon-remote-stage/go1-sim:v1.0
docker login registry.cookcloud.ru
docker pull --platform linux/amd64 "$SIM_IMAGE"
python3 run_local.py --task T2 --sim-only --sim-image "$SIM_IMAGE" --headless --logs
  1. После появления нужного режима в образе остановить запуск через Ctrl+C. Из корня go1-simulator-public запустить пару контейнеров. В примере PARTICIPANT_IMAGE — локальный тег собранного решения с T2. Для T3 и T4 заменить значение --task. Для T5 добавить --course-width 2.0 или --course-width 1.0.
export PARTICIPANT_IMAGE=go1-participant:local
python3 run_local.py --task T2 --sim-image "$SIM_IMAGE" \
  --participant-image "$PARTICIPANT_IMAGE" --headless --logs
  1. Запускатель выводит имя контейнера Simulator и выбранный ROS-домен. Во втором терминале открыть docker exec -it ИМЯ_СИМУЛЯТОРА bash, выполнить source /etc/go1_sim_env.sh, затем ros2 topic list --no-daemon и ros2 topic echo /clock --once. Для T2/T3 должны приходить сообщения /lowstate, для T4/T5 — /imu/data, /scan и изображения. Если Simulator видит датчики, а Participant их не получает, сверить типы, QoS и переданные запускателем ROS_DOMAIN_ID, RMW_IMPLEMENTATION, CYCLONEDDS_URI. Имена топиков начинаются от корня, без префикса /go1. Скрипт запуска · Инструкция по развёртыванию

Два вида времени. Проверку запуска T1 измерять обычными часами. Для поведения робота, частот и пауз использовать /clock и включить use_sim_time=true у узлов. Для T4/T5 обязателен lockstep — согласованное продвижение физики и датчиков. Одна секунда симуляции может занять больше секунды на хосте. Для повторяемых проверок записывать входы, выходы и /clock одного прогона вместе, отмечать версию образа и сцену. Локальные измерения дают оценку готовности, официальные баллы выставляет закрытый Judge. Правила испытаний

T1. Подготовить образ к автоматическому запуску

Основы перед T1

Как собрать образ и запустить контейнер в Docker

Docker — инструмент для сборки образов и запуска программ в контейнерах. В Robohack команда описывает окружение один раз, а организаторы запускают его на своём компьютере. Попробуем весь путь на работающем T1.

Dockerfile — рецепт сборки
В корне Robohack лежит текстовый файл Dockerfile. Строка FROM выбирает базовую среду с ROS 2, RUN устанавливает пакеты, COPY добавляет скрипт команды в образ. ENTRYPOINT ["/entrypoint.sh"] задаёт программу для запуска, а CMD ["ping"] — её аргумент по умолчанию.
Образ и контейнер
Образ — упакованные файлы программы, библиотек и настроек. Контейнер — запущенный экземпляр образа. Из одного образа можно создать десять чистых контейнеров. Поэтому веса модели нужно положить в образ при сборке: файл с ноутбука разработчика на стенде сам не появится.
Платформа и права
linux/amd64 описывает ОС и набор команд процессора. На другом процессоре Docker может использовать эмуляцию при сборке. Внутри образа процесс запускается от обычного пользователя. Проверяйте, что ему доступны веса и разрешена запись туда, где программа создаёт временные файлы.
Точка входа и протокол
Entrypoint — исполняемый файл, которому запускатель передаёт аргумент. Вызов ping здесь означает запрос возможностей. stdout — стандартный вывод, где запускатель читает JSON (текст с именованными полями и значениями). stderr — отдельный поток для диагностики. Даже приветствие перед JSON помешает строгому разбору ответа.
Тег и digest
Реестр — хранилище образов. У организаторов это Harbor. Тег latest — имя, которое можно назначить следующей сборке. Digest — отпечаток конкретного содержимого в реестре. Коммит на GitHub фиксирует исходники, digest в Harbor фиксирует образ. Эти две ссылки позволяют организаторам восстановить именно вашу отправку.

Первый запуск Docker

Где вводить команды. В терминале компьютера с запущенным Docker, в каталоге Robohack, где находятся Dockerfile и entrypoint.sh. Если команда docker ещё не установлена, на macOS используют Docker Desktop, на Linux можно установить Docker Engine с Buildx. Установка Docker.

1. Проверить доступ к Docker

docker version

В выводе должны быть разделы Client и Server. Если виден только клиент и ошибка подключения, запустите Docker Desktop или службу Docker Engine и повторите команду.

2. Собрать образ из Dockerfile

docker buildx build --platform linux/amd64 --load -t go1-t1:local .

Точка в конце указывает каталог сборки. --platform выбирает платформу стенда, -t даёт образу имя go1-t1:local, а --load помещает его в локальный Docker. Для первой сборки нужен интернет.

3. Посмотреть, что собралось

docker image inspect --format '{{.Os}}/{{.Architecture}} {{.Config.User}}' go1-t1:local

Для этого репозитория ожидается linux/amd64 participant. Первое значение — платформа, второе — пользователь, от которого запускается программа.

4. Создать контейнер и вызвать ping

time docker run --rm --pull never --platform linux/amd64 --network none \
  --cap-drop ALL --security-opt no-new-privileges \
  --entrypoint /entrypoint.sh go1-t1:local ping

Docker берёт локальный образ и вызывает внутри него /entrypoint.sh ping. --network none отключает сеть, --rm удаляет завершившийся контейнер. Образ остаётся на компьютере. Ожидаемый ответ программы в stdout:

{"protocol_version":"1.0","supported_tasks":[],"self_trained_rl":false,"preferred_speed_mps":null}

Пустой supported_tasks соответствует текущей версии проекта. time отдельно выводит длительность запуска. Условие T1 — не более 10 секунд и код завершения 0.

Проверить себя

Образ скачан, но при старте программа пытается получить модель из интернета. Пройдёт ли допуск?

Нет. Скачайте веса на этапе сборки, включите их в образ и повторите запуск без сети. Успешный ping отдельно от запуска модели проверяет лишь часть контракта.

Задание и реализация

Результат. Один образ linux/amd64 с Ubuntu 22.04, ROS 2 Humble, Eclipse Cyclone DDS и rmw_cyclonedds_cpp. Participant работает на CPU под обычным пользователем. В Robohack базовый образ закреплён по digest, пользователь имеет UID/GID 10001. Dockerfile · Стек проекта

Порядок работы и приёмки

  1. Положить исполняемый /entrypoint.sh, зависимости, конфигурации и веса в образ при сборке. Для каждого реализованного задания точка входа должна поднять соответствующие ROS-узлы и поддерживать их работу до остановки контейнера инфраструктурой.

  2. Собрать и проверить образ по командам README. Проверить архитектуру и пользователя, затем запустить /entrypoint.sh ping с --network none. Успех — код 0 за ≤10 секунд реального времени, в stdout ровно один JSON-объект, диагностика допускается в stderr. Для сегодняшнего образа ожидается строка ниже. Сборка и автономная проверка

    {"protocol_version":"1.0","supported_tasks":[],"self_trained_rl":false,"preferred_speed_mps":null}

  3. При добавлении каждого режима повторить автономную проверку и отдельный запуск этого режима рядом с Simulator. В supported_tasks перечислить работающие режимы латиницей, например ["T2"] после готовности фильтра. При добавлении T3 согласовать скорость и признак обучения с фактическими весами. Изоляция сети в тесте ping проверяет автономность образа. В испытаниях T2–T5 контейнерам нужна связь между собой по ROS 2 при отсутствии интернета.

T2. Отфильтровать команды суставам

Основы перед T2

Как ROS 2 передаёт команду суставу

ROS 2 — набор инструментов для программ, которые обмениваются данными робота. MuJoCo — симулятор физики: он рассчитывает движение виртуального Go1 и сообщает, в каком положении оказались суставы. В T2 между источником команд и симулятором стоит программа команды — Safety Block, фильтр безопасности.

Узел, топик и сообщение
Узел ROS 2 — компонент с одной ролью. Топик — именованный канал передачи данных. Сообщение задаёт структуру одного значения в этом канале. В T2 фильтр подписан на /lowcmd_bare и публикует /lowcmd. Одноимённый топик с несовместимым типом не создаст рабочую связь.
Издатель и подписчик
Издатель отправляет сообщения в топик. Подписчик получает новые сообщения из него. Один узел может делать и то и другое: фильтр читает предложенную команду из /lowcmd_bare и отправляет проверенную в /lowcmd. Ещё один вход, /lowstate, несёт измерения симулятора.
Положение и управление
У Go1 четыре ноги по три сустава. q задаёт целевой угол в радианах, dq — целевую угловую скорость, tau — добавочный момент. Коэффициенты kp и kd задают реакцию регулятора на ошибки положения и скорости. Измеренный угол из LowState может отставать от цели в LowCmd.
Конфигурация и переход
Конфигурация — все двенадцать углов одновременно. Две допустимые конфигурации могут соединяться движением, при котором части ног пересекаются. Для локальной проверки разбейте переход на промежуточные конфигурации и проверьте расстояния между выбранными геометриями.
Таймер и пропажа входа
Подписка реагирует на новое сообщение. Таймер срабатывает периодически даже без новых сообщений. Если публиковать только из обработчика подписки, исчезновение входа остановит и выход. Хранение безопасной цели и отдельный таймер позволяют продолжить удержание.

Прочитать измерение и найти фильтр

Где вводить команды. Запустите нужный режим по разделу «Локальный стенд». Во втором терминале на компьютере выполните docker exec -it ИМЯ_СИМУЛЯТОРА bash, подставив имя из строки Simulator=. В открывшейся оболочке выполните source /etc/go1_sim_env.sh. Команды ниже вводите в этой оболочке.

1. Увидеть датчик в MuJoCo

ros2 node list
ros2 topic list -t
ros2 topic echo /lowstate --once

Первые две команды перечисляют узлы, затем каналы и их типы. Найдите /lowstate типа unitree_go/msg/LowState. Последняя команда ждёт одно сообщение и завершается. Это можно попробовать уже в режиме --sim-only.

2. Проверить выход своего узла

ros2 topic info /lowcmd --verbose
ros2 interface show unitree_go/msg/LowCmd

Когда T2 реализован и Participant запущен, у /lowcmd должен быть издатель Safety Block. Первая команда показывает издателей и подписчиков. Вторая показывает поля типа сообщения, даже если фильтр ещё не запущен.

Проверить себя

Робот получил безопасную цель 0,20 рад, успел дойти до 0,16 рад и потерял вход. Какую цель удерживать?

Последнюю принятую безопасную цель 0,20 рад. Измерение 0,16 рад описывает фактический угол в этот момент. При удержании скорость и добавочный момент задаются нулевыми.

Задание и реализация

Контракт. В MuJoCo Lowlevel Judge подаёт /lowcmd_bare (unitree_go/msg/LowCmd). Узел Safety Block получает состояние из /lowstate (unitree_go/msg/LowState) и один публикует /lowcmd (LowCmd). Judge проверяет сам выход фильтра. Порядок ног — FR, FL, RR, RL, внутри каждой — hip, thigh, calf. Пределы для каждой ноги в радианах соответственно [−0,863; 0,863], [−0,686; 4,501], [−2,818; −0,888]. Сводное ТЗ, §4

При нарушении можно удержать предыдущую безопасную цель либо подобрать безопасную коррекцию и повторно проверить переход. Модель и перечень пар
  4. Продолжать публиковать по таймеру даже при потере входа. Через ≤0,5 с симуляции перейти на удержание последней принятой цели с dq=0, tau=0 и допустимыми kp, kd. При движении измеренное положение может отличаться от цели.

T3. Пройти 3 метра с RL-политикой

Основы перед T3

Как RL-политика управляет ходьбой

Обучение с подкреплением (reinforcement learning, RL) — способ научить модель выбирать действия по результатам попыток. Например, при обучении можно поощрять движение с заданной скоростью и штрафовать падение. Для испытания нужна уже обученная модель, способная выдавать команды на каждом шаге.

Политика и инференс
Политика — функция, которая по наблюдению выбирает действие. При обучении с подкреплением (RL) её параметры подбирают по награде в серии попыток. На испытании выполняется инференс: готовая модель по новым данным вычисляет очередное действие на CPU.
Веса модели и команда скорости
Веса — числа, которые модель сохраняет после обучения. В T3 на входе есть желаемая скорость корпуса. Сообщение типа Twist содержит линейную и угловую скорости. Например, linear.x = 0.3 означает запрос движения вперёд со скоростью 0,3 м/с. Расчёт целей для отдельных суставов выполняет политика.
Наблюдение
Вектор наблюдения собирают в том порядке, единицах и масштабе, которые использовали при обучении. Например, перестановка показаний левых и правых суставов сохранит размер входа, но изменит смысл чисел для сети. Состав наблюдения определяется выбранной моделью.
Действие и обратная связь
Выход сети часто выражает поправку к нейтральной позе. Адаптер переводит выход конкретной политики в цели суставов. Safety Block проверяет их, симулятор делает шаг и возвращает новое состояние. Так политика видит последствия предыдущего действия.
Эпизод и критерий успеха
Эпизод — одна попытка с чистого старта. После прогрева считают смещение вдоль первоначального направления. Если робот прошёл по дуге 3,2 м, но сдвинулся вперёд только на 2,6 м, условие дальности ещё не достигнуто.

Передать команду ходьбы

Где вводить команды. Запустите нужный режим по разделу «Локальный стенд». Во втором терминале на компьютере выполните docker exec -it ИМЯ_СИМУЛЯТОРА bash, подставив имя из строки Simulator=. В открывшейся оболочке выполните source /etc/go1_sim_env.sh. Команды ниже вводите в этой оболочке.

1. Разобрать сообщение скорости

ros2 interface show geometry_msgs/msg/Twist

В сообщении две части: linear для движения в м/с и angular для поворота в рад/с. Структуру типа можно посмотреть в симуляторе до реализации T3.

2. Задать скорость в локальном T3

ros2 topic pub --rate 10 /cmd_vel geometry_msgs/msg/Twist '{linear: {x: 0.3}, angular: {z: 0.0}}'

Выполняйте при работающем Participant с T3. Команда повторяет запрос скорости 10 раз в секунду до Ctrl+C. Для тренировки выбрано 0,3 м/с. Для репетиции зачёта используйте скорость, которую возвращает ваш ping.

3. Проследить один шаг до симулятора

ros2 topic echo /lowcmd_bare --once
ros2 topic echo /lowcmd --once

Откройте ещё одну оболочку Simulator и подключите то же окружение. В первом канале видны цели, рассчитанные политикой, во втором — команды после Safety Block. Это два отдельных снимка потока. Для сравнения одного и того же шага запишите оба топика вместе с /clock.

Проверить себя

Одна из десяти попыток успешна, команда дообучила модель. Что нужно кроме флага в ping?

Веса полученной политики, конфигурация дообучения, журналы и результаты. При подтверждении этих материалов один успешный эпизод даёт 5 баллов за движение и ещё 15 за обучение.

Задание и реализация

Контракт. В MuJoCo без камер Judge передаёт geometry_msgs/msg/Twist в /cmd_vel. Политика получает команду скорости и /lowstate, вычисляет цели 12 суставов и выдаёт /lowcmd_bare. Дальше работает Safety Block из T2. Во всех 10 эпизодах linear.x равна одной заявленной в ping скорости от 0,1 до 0,6 м/с, linear.y и angular.z равны нулю. Условия T3

Пример реализации

  1. Выбрать готовую, обученную командой или дообученную политику. Зафиксировать состав и нормализацию наблюдений, порядок суставов, исходную позу, частоту инференса и преобразование выхода модели в цели. Проверить на одном записанном состоянии, что левые и правые суставы получают свои команды.
  2. Упаковать веса и CPU-среду инференса. На старте каждого эпизода заново инициализировать историю наблюдений и состояние политики. Записать вход и выход Safety Block при переходе от стойки к ходьбе. Частое отклонение целей — повод сверить масштаб действий, частоту и начальную позу.
  3. Подобрать устойчивую скорость в разрешённом диапазоне и вернуть её в preferred_speed_mps. При собственном обучении или дообучении указать self_trained_rl=true и приложить веса, конфигурацию, журналы экспериментов и результаты. Для готовой сторонней политики указать false.

Локальная приёмка. Выполнить 10 запусков с одной скоростью, каждый раз пересоздавая оба контейнера. Из внешнего узла подать /cmd_vel. Отвести 1,5 с sim time на прогрев, затем до 90 с на зачёт. Для каждого запуска записать проекцию перемещения на исходное направление, время достижения 3 м и факт падения. Падение фиксировать при высоте корпуса <0,16 м, |roll| >50° или |pitch| >50°, если соответствующее нарушение длится непрерывно >0,5 с. При восстановлении сбросить отсчёт. Пройденные по дуге 3 м сами по себе не подтверждают смещение вперёд на 3 м.

Баллы. Хотя бы один успешный эпизод даёт 5, от семи из десяти — ещё 10. Подтверждённое собственное обучение или дообучение при хотя бы одном успехе даёт ещё 15. Таким образом, готовая политика может принести до 15, подтверждённая собственная — до 30. Сохранить таблицу десяти эпизодов рядом с версией весов, чтобы при сдаче связать результат с конкретным образом.

T4. Оценить фактическую траекторию

Основы перед T4

Как одометрия измеряет движение корпуса

Одометрия — оценка того, как робот переместился и повернулся относительно старта. Gazebo моделирует мир и датчики, а CHAMP управляет шагами ног по заданной скорости. В T4 скорость задаёт судья. Задача команды — восстановить фактическую траекторию по показаниям датчиков.

Поза и фрейм
Поза объединяет положение и ориентацию. Значения координат имеют смысл относительно системы отсчёта — фрейма. trunk прикреплён к корпусу. odom задаёт локальную систему, в которой мы отслеживаем движение корпуса от старта.
Крен, тангаж и курс
Ориентация описывает поворот корпуса. Крен (roll) — наклон вбок, тангаж (pitch) — наклон носом вверх или вниз, рыскание (yaw) — поворот вокруг вертикали. ROS часто передаёт ориентацию кватернионом — четырьмя числами, которые вместе задают один поворот.
TF и временная метка
TF — дерево преобразований между фреймами. Ребро odom → trunk сообщает, где расположен корпус в системе одометрии. Время входит в смысл измерения: преобразование после поворота даст неверный результат для снимка, сделанного до поворота.
Датчики и объединение оценок
IMU — инерциальный измерительный модуль. Его гироскоп измеряет угловую скорость, акселерометр — удельное ускорение. Лидар измеряет расстояния по направлениям. Сопоставив два скана неподвижных стен, можно оценить сдвиг и поворот датчика. IMU помогает отслеживать быстрые повороты между сканами.
Дрейф и относительная ошибка
Дрейф — накопленное изменение оценки, в том числе когда робот уже стоит. RPE (Relative Pose Error) в этом задании показывает ошибку перемещения на участке фактического пути. При истинном сдвиге (1, 0) м и оценке (0,9, 0,1) м ошибка составляет около 14%: учитываются обе координаты.

Увидеть движение в сообщениях

Где вводить команды. Запустите нужный режим по разделу «Локальный стенд». Во втором терминале на компьютере выполните docker exec -it ИМЯ_СИМУЛЯТОРА bash, подставив имя из строки Simulator=. В открывшейся оболочке выполните source /etc/go1_sim_env.sh. Команды ниже вводите в этой оболочке.

1. Посмотреть измерение и его время

ros2 topic echo /imu/data --once

Можно выполнить в режиме T4 с --sim-only. Найдите header.stamp — время измерения, и angular_velocity — показания гироскопа. Компонента z показывает скорость вращения вокруг оси Z датчика в рад/с.

2. Сопоставить два выхода одометрии

ros2 topic echo /odom --once
ros2 run tf2_ros tf2_echo odom trunk

Когда узел T4 работает, в сообщении ожидаются header.frame_id: odom и child_frame_id: trunk. Вторая команда периодически выводит положение и поворот корпуса в системе odom. При движении значения обновляются. Остановите просмотр через Ctrl+C. Сравнивать позы следует на один момент по времени симуляции.

Проверить себя

Одометрия рисует идеальный квадрат, хотя робот фактически уходит с прямой. Хорошая ли это оценка?

Нет. Judge сравнивает с фактическим движением. Для диагностики совместите начальные позы, сопоставьте измерения по времени и измерьте ошибку на последовательных участках фактического пути.

Задание и реализация

Контракт. В Gazebo Highlevel с lockstep команды /cmd_vel подаёт Judge. Participant оценивает движение по IMU, лидару, суставам, фронтальной RGB-D камере и другим доступным публичным измерениям. Выходы — /odom типа nav_msgs/msg/Odometry и динамическое преобразование TF odom → trunk. Оба должны описывать одну позу в одно время с частотой ≥20 Гц по /clock. Условия T4

Пример реализации

  1. Сверить временные метки /imu/data и /scan, проверить TF от датчиков до корпуса. Как отправную точку можно взять изменение ориентации по гироскопу и оценку смещения сопоставлением соседних сканов. При слабых геометрических ориентирах проверить, помогает ли фронтальная камера.
  2. Объединить измерения в оценку позы, обновлять её между сканами по IMU. Из одного состояния публиковать /odom с header.frame_id="odom", child_frame_id="trunk" и соответствующий TF. Проверять конечность значений и единичную норму кватерниона. Стартовую позу можно выбрать нулевой, при оценке начальные позы совмещаются.
  3. Отдельно отладить остановку. На неподвижных данных оценить смещение нуля IMU и проверить, что шум датчиков не накапливается как движение. На прямом участке сверять поворот по датчикам — у модели Gazebo заметен увод курса даже при нулевой заданной угловой скорости.

Локальная приёмка. Внешний узел командует сценарием «стойка → четыре прямых по 0,2 м/с с четырьмя поворотами на 90° по 0,3 рад/с → остановка → 10 с покоя». Записать /odom, /tf, /clock и отдельно доступную в публичном Gazebo /odom/ground_truth. Совместить начальные позы и сравнить оценки в одни и те же моменты.

Проверка Как считать Баллы
Выходной контракт Для одометрии и TF проверить ≥20 Гц sim time, фреймы, согласованность поз и меток времени 3
Относительная ошибка перемещения (RPE) Разбить фактический путь на последовательные участки около 1 м. На каждом взять норму разности оценённого и истинного векторов перемещения в согласованных координатах, разделить на фактическую длину участка. Усреднить ≤50% — 5, ≤20% — ещё 6

T5. Пройти неизвестную трассу и распознать метки

Основы перед T5

Как Go1 использует Nav2 и распознаёт ArUco

Автономная навигация начинается с конечной позы: куда прийти и куда смотреть на финише. Nav2 (Navigation 2) — набор программ ROS 2, которые строят путь и управляют движением по нему. Вторая задача в этом же проходе — прочитать номера квадратных меток ArUco на изображениях с камер.

Локализация и карта
Одометрия даёт непрерывное локальное движение. Локализация связывает его с системой map, в которой задана цель. Цепочка map → odom → trunk позволяет вычислить положение корпуса на карте. SLAM — один из способов одновременно строить карту по наблюдениям и уточнять положение.
Сканирование и распознавание
Лидар измеряет расстояния до окружающих поверхностей. Так Nav2 получает сведения о препятствиях. Цветная камера даёт кадр, в котором детектор ищет рисунок метки. У этих данных разные получатели: расстояния помогают выбрать движение, распознанный ID получает судья.
Nav2 и карта стоимости
Nav2 — навигационный стек. Карта стоимости описывает препятствия и близость к ним. Глобальный планировщик выбирает путь, локальный контроллер рассчитывает скорость для ближайшего участка, CHAMP в симуляторе исполняет её. В узком проходе важны ширина корпуса и запас у стены.
Action и фактический финиш
Action в ROS 2 — интерфейс длительной операции. Клиент отправляет цель, сервер принимает её, может передавать обратную связь и возвращает результат. В T5 Judge — клиент, Nav2 — сервер. Статус успеха отражает оценку навигации. Судья отдельно измеряет истинные положение и угол.
RGB-D и ArUco
RGB-D камера даёт цвет и глубину. ArUco — квадратная метка с кодом из заданного словаря. Детектор ищет её границы в кадре, распознаёт ID и отправляет текущие обнаружения. Набор уникальных ID за весь проход накапливает Judge.

Проверить две независимые части T5

Где вводить команды. Запустите нужный режим по разделу «Локальный стенд». Во втором терминале на компьютере выполните docker exec -it ИМЯ_СИМУЛЯТОРА bash, подставив имя из строки Simulator=. В открывшейся оболочке выполните source /etc/go1_sim_env.sh. Команды ниже вводите в этой оболочке.

1. Найти навигационный сервер

ros2 action list -t
ros2 action info /navigate_to_pose

После запуска T5 в списке должен появиться /navigate_to_pose типа nav2_msgs/action/NavigateToPose. В сведениях ожидается один Action-сервер в Participant. Теперь клиент может отправить цель в системе map.

2. Проверить, откуда берутся координаты

ros2 run tf2_ros tf2_echo map trunk

Должно появиться преобразование от системы карты к корпусу. Если вывод продолжает ждать фрейм, проверьте отдельно пары map odom и odom trunk той же командой. Завершите просмотр через Ctrl+C.

3. Прочитать результат детектора

ros2 topic echo /aruco/detections --once

Когда камера видит метку, ищите строковое поле data с JSON, например {"ids":[7]}. При пустом кадре допустим пустой список или пауза в публикации. В последнем случае команда будет ждать следующего сообщения.

Проверить себя

Nav2 вернул успех. Истинная ошибка положения 0,3 м, ошибка ориентации 35°. Засчитан ли финиш?

Нет. Положение укладывается в 0,5 м, но угол превышает 30°. Оба условия должны выполняться одновременно. Баллы за подтверждённые видимые метки оцениваются отдельно.

Задание и реализация

Контракт. Один непрерывный проход в Gazebo Course с CHAMP и lockstep. Judge задаёт начальную позу и передаёт цель в map клиентом /navigate_to_pose типа nav2_msgs/action/NavigateToPose. В Participant обязателен сервер Nav2. Старт — (0, 0), yaw 0°, вперёд вдоль +X. Готовой карты скрытой трассы и отдельной разведки нет. Условия T5

Часть решения Что получает Что выдаёт
Одометрия T4 Датчики движения /odom, TF odom → trunk
Локализация и представление препятствий Одометрия, лидар, начальная поза TF map → odom и данные для планирования. Возможный вариант — SLAM во время движения
Nav2 Цель, TF map → odom → trunk, карты стоимости План и /cmd_vel для CHAMP
Детектор ArUco Изображения камер /aruco/detections типа std_msgs/msg/String, поле data содержит JSON текущих наблюдений

Порядок интеграции

  1. Запустить одометрию, локализацию и Nav2. Настроить базовый фрейм trunk. До отправки цели проверить доступность map → trunk по TF на времени датчика и готовность action-сервера (ros2 action info /navigate_to_pose). У каждого динамического преобразования должен быть один издатель.
  2. Начать с публичной трассы шириной 2 м. Отправить тестовую цель в map, убедиться, что Nav2 строит путь и CHAMP исполняет /cmd_vel. Затем перейти на 1 м — это ширина проходов скрытой трассы. Настроить габарит робота, запас до стен и скорость в поворотах. При уводе курса корректировать движение по оценённой позе. Judge в T5 курс не исправляет.
  3. Подключить камеры /camera, /camera_chin, /camera_left, /camera_right, /camera_rearDown. Для префикса доступен RGB image_raw в rgb8, глубина depth/image_raw в 32FC1 и соответствующие camera_info. Фронтальная камера даёт 640×480 при 15 Гц, остальные — 464×400 при 10 Гц sim time. Сверить QoS с симулятором. Справочник камер, §8.4
  4. Детектировать словарь DICT_4X4_50. Полная сторона метки — 0,25 м, чёрной области — 0,1875 м, центр на высоте 0,36 м. Публиковать увиденные сейчас ID, например {"ids":[3,7]}. При пустом кадре допустимы отсутствие сообщения или {"ids":[]}. Judge сам накапливает уникальные ID и проверяет видимость в момент регистрации. Подбор ID аннулирует баллы за метки.
  5. Повторить полный проход из чистого старта на обеих трассах с включёнными пятью камерами на CPU. Сверять кадр и момент публикации детекций. Очередь старых кадров может дать правильный ID слишком поздно. Проверить несколько целей и поворотов, чтобы маршрут строился по датчикам при изменении обстановки.

Локальная приёмка и баллы

Критерий Проверка после прохода Баллы
Финиш По фактической позе одновременно ошибка положения ≤0,5 м и ошибка yaw ≤30°. Записать обе ошибки вместе со статусом action 15
Метки Разделить число уникальных верно зарегистрированных видимых ID на число уникальных меток трассы. Повторы одного ID считать один раз ≥50% — 5, ≥80% — ещё 7, независимо от финиша
Контакты Финиш достигнут, за весь проход нет недопустимого контакта по критерию ниже 8

Для проверки контактов на локальном стенде нужны данные физики Gazebo. Для каждой пары коллизионных объектов сложить модули сил по точкам контакта за один шаг, считая каждую силу один раз. Порог — ≥5 Н непрерывно ≥0,02 с sim time, при снижении ниже порога отсчёт начинается заново. Стопы могут касаться разрешённого пола. Учитываются удары о стены и препятствия любой частью робота и касание пола другими частями тела. Самоколлизии из этой метрики исключены. Если записаны только видео и топики Nav2, по ним можно найти подозрительное место, но количественный критерий контактов остаётся непроверенным.

Сдача одного проверенного образа

  1. Зафиксировать исходники, Dockerfile, конфигурации и инструкцию сборки в публичном GitHub-репозитории. Для бонуса T3 приложить материалы обучения. Сохранить ссылку на конкретный коммит вида https://github.com/<команда>/<репозиторий>/commit/<полный_SHA>.
  2. Из этого коммита собрать Participant под linux/amd64 и опубликовать в назначенный проект Harbor по командам проекта. Получить SHA-256 digest из docker buildx imagetools inspect. Команды публикации
  3. Скачать образ по digest, на этой версии повторить автономный ping и локальный запуск каждого режима из supported_tasks. Сверить заявленную скорость и происхождение весов T3. Для собственной сводки сохранить версию образа и результаты проверок T2–T5.
  4. В личный кабинет передать два значения — ссылку на Git-коммит и полную команду загрузки с реальными именами проекта, репозитория и digest. Формат второго поля — docker pull --platform linux/amd64 registry.cookcloud.ru/<team>/<team>@sha256:<digest>. Проверить, что ссылка открывается, а команда загружает отправленную версию.

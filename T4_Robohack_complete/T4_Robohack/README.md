# T4 — новая реализация, версия 2

Оценка движения Unitree Go1 по лидару и IMU. Исходники переписаны заново; старый scan_odometry.py не используется. Подготовлено для Gazebo Classic Highlevel + CHAMP + lockstep, ROS 2 Humble. В репозиторий команды ничего не отправлено.

## Статус проверки

- 5 тестов ядра: пройдены. Квадрат в искусственной комнате, лазерный шум 0.01 м, наклоны корпуса: RPE 0.159%, дрейф за 10 с 0.00117 м и 0.0417°.
- ROS 2 Jazzy, искусственные датчики: 250 сообщений, 50 Гц sim time; TF совпадает с каждой позой и временной меткой.
- Эти результаты НЕ являются испытанием Gazebo или оценкой Judge.
- Сборка Docker, запуск на Humble и реальные RPE/дрейф НЕ проверены: среда разработки не даёт доступа к Docker.
- 20/20 не подтверждены. Плоская оценка позиции (z=0), отсутствие визуальной резервной одометрии и потеря геометрии лидара — ограничения.

## Файлы

- `core.py`: интерполяция ориентации, проекция лучей, робастное сопоставление сканов с опорным сканом.
- `node.py`: ROS 2-узел, синхронизация датчиков, /odom, TF, /t4/status.
- `Dockerfile`, `entrypoint.sh`, `build.sh`: отдельный контейнер T4, без интеграции T2/T3.
- `record_trial.py`: ТОЛЬКО локальный испытатель, умеет командовать квадрат и писать истинную/оценённую траектории и TF.
- `metrics.py`: расчёт локальных метрик по CSV.
- `gazebo_window.sh`: повторный запуск GUI у уже работающего gzserver с сохранением журналов.
- `ros_smoke.py`, `tests/`: проверки ROS-контракта и алгоритма.

## Алгоритм и контракт

Входы рабочей программы: /scan (base_scan), /imu/data (imu_link), /clock. Нет подписки на /cmd_vel, ground truth или карту полигона. Лидар закреплён на trunk со смещением (0.22, 0, 0.11) м и нулевым вращением, IMU соосна корпусу — по публичному URDF. Смещение лидара задаётся параметром `laser_offset`.

IMU должна предоставлять валидную ориентацию. Для времени скана используется SLERP между IMU-измерениями; скан ждёт следующего измерения IMU. Крен и тангаж учитываются при проекции лучей; курс задаётся IMU относительно начального курса. Робастный point-to-line ICP оценивает XY относительно опорного скана. Нормали не строятся через пропущенные лучи. Низкое перекрытие, вырожденная геометрия и неправдоподобные скачки отклоняются. На месте опорный скан не обновляется, поэтому шум не интегрируется по кадрам.

Выходы: /odom, TF odom→trunk с согласованными позой и stamp, целевой таймер 50 Гц sim time. Pose — в odom, twist — в trunk. При потере датчиков поза удерживается, twist обнуляется, covariance увеличивается; это не считается успешным слежением. Ошибки видны в /t4/status. После сброса времени состояние сбрасывается. При полной потере локализации нет глобального поиска и гарантированного восстановления.

## Собрать контейнер

```bash
bash build.sh
```

Скрипт выбирает buildx, если он есть, иначе обычный Docker build с legacy builder. Образ: `go1-t4:v2`. Сборка требует сети; выполнение не требует загрузки зависимостей. В submission-образ копируются только core.py, node.py и entrypoint.sh; испытатель и ground truth туда не входят. ping заявляет только T4.

## Gazebo

Для нового испытания остановите прежний запуск через Ctrl+C в его терминале, чтобы не запускать конфликтующие Gazebo master. Затем:

```bash
cd ~/go1-simulator-public
python3 run_local.py --task T4 \
  --sim-image registry.cookcloud.ru/go1-hackathon-remote-stage/go1-sim:v1.0 \
  --participant-image go1-t4:v2 --domain 151 --gui --logs
```

Если gzserver работает, но gzclient упал, из папки T4:

```bash
bash gazebo_window.sh
```

Скрипт автоматически выбирает единственный контейнер с официальным образом. Если контейнеров несколько, передайте точное имя аргументом. Он проверяет наличие gzserver и отсутствие gzclient, сохраняет results/simulator.log, запускает только окно с Qt xcb и программным OpenGL. Это диагностический вариант, а не подтверждённое исправление прежнего падения. Он не меняет права X11, VPN или систему. При ошибке смотрите results/gzclient.log.

## Измерить точность в публичном симуляторе

Испытатель командует движение только при явном --drive и после /go1_ready и появления /odom, truth и TF. Не запускайте его одновременно с Judge или другой программой управления. Он выполняет начальную остановку, четыре прямых участка по 5.5 с при 0.2 м/с, четыре поворота при 0.3 рад/с, 5 с установления и 11 с покоя. Коррекции курса нет; фактический путь может существенно отличаться от квадрата.

Запустите испытатель на хосте с ROS 2, numpy и scipy, в том же домене и предпочтительно с CycloneDDS. Для имеющейся Ubuntu/Jazzy пакет CycloneDDS устанавливается отдельно при необходимости:

```bash
sudo apt install ros-jazzy-rmw-cyclonedds-cpp
source /opt/ros/jazzy/setup.bash
export ROS_DOMAIN_ID=151
export RMW_IMPLEMENTATION=rmw_cyclonedds_cpp
export CYCLONEDDS_URI=file://$HOME/go1-simulator-public/user_data/ros2_custom_config_setup/cyclonedds_local.xml
# Из папки T4:
OPENBLAS_NUM_THREADS=1 /usr/bin/python3 record_trial.py --drive
```

Тест Jazzy↔Humble ещё не выполнен; эталонная среда сдачи — Humble внутри образа. Сохраняются CSV и metrics.json в results/<время>. Если ground truth отсутствует, испытатель не начинает движение. Тайм-аут по настенным часам — 1800 с, он изменяется через --wall-timeout.

Локальная метрика делит фактическую 3D-траекторию на последовательные участки ≥1 м и сравнивает относительные перемещения в системе корпуса начала каждого участка. Используется SLERP ориентаций и линейная интерполяция позиций. Проверяются изменение позиции/ориентации за 10 с, средние частоты и совпадение TF. Это реализация по публичному описанию, не точная копия закрытого Judge. Проверяйте максимальные интервалы, потерю сообщений и actual_end_displacement_m: команда остановки не гарантирует физическую неподвижность.

Для максимума нужны: /odom и TF ≥20 Гц sim time; RPE ≤20%; дрейф ≤0.10 м и ≤5°. Средняя частота сама по себе не гарантирует отсутствие провалов публикации. До измерения всех критериев в Gazebo не заявляйте максимальный балл.

## Проверка потерь TF (исправление испытателя)

В первом реальном испытании записано 50 Гц /odom, но только 25.54 Гц TF; максимальный интервал TF 0.22 с. В record_trial.py была очередь qos_profile_sensor_data (Best Effort, depth=5), общая для всех сообщений /tf. Она заменена на Reliable depth=1000; добавлены tf_max_gap_s и tf_gaps_over_50ms. Частота и сам алгоритм одометрии не изменены; образ пересобирать для изменения испытателя не нужно.

Контролируемый тест пакетной доставки (30 сообщений корпуса + фоновые TF): старая очередь получила 0/30, новая 30/30. Это воспроизводит механизм потерь, но НЕ доказывает, что все пропуски реального запуска вызваны именно им. Для проверки работающего Gazebo запустите tf_probe.py в той же ROS-сети: он одновременно слушает /tf обоими способами и сопоставляет /odom в течение 20 секунд настенного времени; команд движения нет.

Из папки T4 при работающем контейнере go1-t4-odom:

```bash
docker cp tf_probe.py go1-t4-odom:/tmp/tf_probe.py
docker exec go1-t4-odom bash -c 'source /opt/ros/humble/setup.bash; python3 /tmp/tf_probe.py'
```

Если tf_reliable получает ~50 Гц с matched_fraction близкой к 1, а tf_old теряет сообщения, причина в приёмнике подтверждена. Если теряют оба, проверять публикацию/DDS/нагрузку далее; не выставлять 20/20 только по синтетическому тесту.

Последующее живое A/B-измерение не подтвердило исправление: /odom 50 Гц, tf_old 15.77 Гц, tf_reliable 14.83 Гц. Причина реальных потерь ещё не установлена. tf_probe.py теперь по умолчанию использует один Reliable-приёмник, очередь 10000 и счётчики всего потока по парам frame_id/child_frame_id. Старый одновременный режим доступен через --mode both. Не считайте увеличение очереди доказанным исправлением.

## Быстрый приём TF: raw-фильтр

Приёмник испытателя теперь подписывается на сериализованные /tf (`raw=True`). Пакеты без строк odom и trunk отбрасываются до создания Python-объектов суставов. Кандидаты декодируются штатным ROS-декодером и проверяются по точным frame_id/child_frame_id. Позы и метки времени не изменяются, смешанные пакеты с корпусом и суставами поддерживаются.

Файлы: tf_receive.py (общий фильтр), tf_probe.py (режим fast по умолчанию), record_trial.py (фильтр включён). Алгоритм node.py и образ go1-t4:v2 не менялись. При запуске скопированной диагностики нужно копировать также tf_receive.py в ту же папку.

```bash
docker cp tf_probe.py go1-t4-odom:/tmp/tf_probe.py
docker cp tf_receive.py go1-t4-odom:/tmp/tf_receive.py
docker exec go1-t4-odom bash -c 'source /opt/ros/humble/setup.bash; python3 /tmp/tf_probe.py --mode fast'
```

Проверки: 3 теста настоящей CDR-сериализации пройдены. Обработка 10500 пакетов (20 пакетов по 12 суставов на один корпус) заняла 2.5827 с с полным разбором и 0.0255 с с фильтром; оба варианта сохранили все 500 трансформаций корпуса. ROS smoke с raw-приёмником: 250/250 пар odom/TF, 50 Гц. Это не испытание нагрузки всего DDS: остаточная задержка проверяется в Gazebo по end_lag_vs_odom_s и full_odom_coverage. Новый raw-приёмник на живом Gazebo пока не проверен.

## Увеличенный квадрат

После перезапуска симулятора в исходную позу и запуска одометрии в домене 151:

```bash
bash run_trial.sh --side 2
```

Сторона задаётся в метрах, скорость остаётся 0.2 м/с. При --side 2 прямой участок длится 10 с, суммарный сценарий с остановками и поворотами — около 82 с sim time. Это номинальный квадрат: CHAMP может отклоняться от курса. Смотрите на фактическое движение и остановите тест Ctrl+C, если робот упирается в стену. Для сравнения запусков используйте одинаковую исходную позу. Прежний тест: --side 1.1. Образ пересобирать не нужно: испытатель подключается с диска.
